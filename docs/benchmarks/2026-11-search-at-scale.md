# Поиск на большом индексе, 2026-11-05

Замер сделан инструментом `tools/Recall.SearchBench` на синтетическом индексе: 20 000 файлов, по одному сегменту в 180 слов, словарь из 20 000 слов, 20 000 векторов по 384 числа. Машина: AMD Ryzen AI 9 HX 370, сборка Release, лучший из трёх прогонов после прогрева. Числа дрожат на 10-20 мс. На сотнях тысяч файлов замеров нет: генерация индекса идёт около 17 мс на файл, то есть сто тысяч файлов это почти полчаса. Рост на больших индексах оценён по формулам ниже, не измерен.

Запуск:

```cmd
Recall.SearchBench --db <новый файл> --files 20000 --dim 384
Recall.SearchBench --db <файл> --run
```

## Результат

| Запрос | До | После |
|---|---|---|
| Слово из двух букв, которое есть в четверти текстов | 994 мс | около 100 мс |
| Слово из трёх и более букв, есть почти в каждом файле (FTS) | 450 мс | 109 мс |
| Перебор всех векторов (поиск по смыслу) | 105-127 мс | 1 мс, пока копия в памяти (первый поиск после изменений 105-127 мс) |
| Редкие слова, фразы, фильтры `in:` и `type:`, имя файла | 9-25 мс | без изменений |

## Что изменено

- **Короткие слова (1-2 буквы).** Файлы перебираются от новых к старым по индексу `files_mtime`, поиск останавливается на нужном числе совпадений. Строки сначала отсеивает быстрый `instr` по вариантам регистра, и только потом managed-функция. Для слова, которого нет вообще, перебор всё равно идёт по всей базе (около 1.5 мкс на сегмент в SQLite).
- **Частые слова в FTS.** Столбец сниппета в запросе пустой, потому что движок всё равно заменяет его окном текста у каждого возвращаемого результата. Без фильтров `in:`, `type:`, `after:`, `before:` сегменты сначала выбираются из таблицы FTS по bm25, и соединения с файлами идут только для лучших.
- **Векторы.** Копия всех векторов одного пространства лежит в одном массиве. Она пересобирается после любого изменения векторов, сбрасывается через 2 минуты без поиска и не создаётся, если больше 512 МБ (тогда поиск идёт как раньше, из SQLite).

## Память

Копия векторов занимает `число векторов x размерность x 4 байта`: 40 000 векторов по 384 числа это около 61 МБ, 100 000 это 154 МБ, 500 000 это 768 МБ (выше предела, кэш не создаётся). Для Gemma 2 (768 чисел) вдвое больше.

## Ограничения

- Слово из каждого документа по-прежнему сортируется по bm25 целиком: порядка 5 мкс на совпадение.
- Имена файлов ищутся перебором путей.
- Сброс кэша по счётчику работает, пока векторы пишет тот же процесс, который отвечает на поиск (агент). Другой процесс, пишущий в базу, кэш не сбросит.
