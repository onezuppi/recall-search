# Plan 1 measurements, 2026-11-04

The measurements come from one developer machine. The numbers describe this machine and these folders. They are not a general result.

The previous version of this file (2026-11-03) is outdated. In it, 314 Office files failed with an xml:space error, and the OCR numbers were wrong because of a shared OCR engine. Both problems are fixed and the measurements are repeated.

## Conditions

| Parameter | Value |
|---|---|
| CPU | AMD Ryzen AI 9 HX 370, 24 logical cores |
| Memory | 31 GB |
| Build | Release (`dotnet publish -c Release`) |
| Worker threads | 12 (default: half of the logical cores) |
| OCR | Windows.Media.Ocr, languages `ru` and `en-US`, engine pool sized to the thread count |
| Index | new file in the scratch folder, outside the Recall Search profile |

Command:

```powershell
Recall.Agent.exe --once --db <scratch>\bench.db --root <Downloads> --root <work files folder on drive C:> --root <ShareX screenshots>
```

With the `--db` parameter, the agent does not take the guard against a second instance. The installed agent was running during the measurement. Its `index.db` was not opened.

The set of roots is small and realistic: the downloads folder, the work files folder, and the screenshots folder. They hold about 4.8 thousand indexable files. Almost all files are screenshots (PNG and JPG).

Exclusions. The `--root` parameter replaces only the list of roots. The agent reads the global exclusion patterns from the user's `config.json`. So the same exclusions apply as in normal work. No patterns were copied into this file.

Stage times are the total busy time across all threads. The exception is Scan, which is the time of one thread. So the sum of the stages is larger than the pass time.

## Pass 1 (empty index)

| Metric | Value |

| Files added | 4 838 |

| OCR of images inside documents | 8.4 s |

| Duplicates by hash | 40 |
| Errors | 4 |

Extract includes OCR of standalone images. This is almost all of the time: the index holds 4 642 unique images out of 4 838 files. Cost estimate: 1 047 s of busy time over 4 642 images gives about 0.23 s per image with two OCR languages. This is an estimate from total time, not a measurement of a single file.

Expected pass time: 1 047 s divided by 12 threads gives about 87 s. The real time is 101 s. The difference is Hash, Scan, and writing to the index.

Index size after pass 1: 27 MB. The index holds 4 896 text segments.

No file is opened or hashed. Walking the metadata of 4 838 files takes half a second.

## Errors by cause

There are 4 errors out of 4 838 files. All have the same cause: `cannot read Office file: File contains corrupted data.`

- 2 files are ordinary XLSX workbooks that the SDK could not open. File integrity was not checked separately.
- 2 files are lock files `~$*.xlsx`. Excel creates them while a workbook is open. They are not real documents.

There are no xml:space errors, no `RecognizeAsync` errors, and no unreadable images.

## Caveats

- One machine, one set of folders, one run. The spread between runs was not measured.
- The set consists almost entirely of images. It does not show the time for large PDFs and Office documents.
- The installed agent was running during the measurement. It may have used CPU and disk. This load was not measured. The `recall.log` file is shared, and the measurement appended lines to it.
- The set holds 37 Office and PDF files. Their share in the numbers is small.
- The OCR cost per image is an estimate from total busy time. This run has no single-file measurement with `--workers 1`.
- Pass 2 shows only the metadata walk of a small set. On a large tree (hundreds of thousands of files), the walk took minutes. The previous measurement took 14 minutes for 206 thousand indexable files in several large roots. Those numbers were taken before the fixes and are given as an order of magnitude. The USN journal service (plan 4) should remove this cost.

## Not measured

- Latency of a single file and OCR throughput on one thread (`--workers 1`).
- Cold start after a machine reboot.
- Search: query time on an index of hundreds of megabytes.
